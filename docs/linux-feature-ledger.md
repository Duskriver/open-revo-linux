更新日期：2026-11-01（Asia/Shanghai）。本台账对应 [项目发展计划](linux-roadmap.md) 的 16 类功能，记录当前交付状态，不是未实现功能的支持承诺。

## 记录规则

每个 `ORL-Fxxx` 是稳定功能 ID。功能拆分时追加子 ID，例如 `ORL-F003.cpu` 和 `ORL-F003.curve`；不得重新编号，也不以导航页数量计算完成率。

实现、运行可用性和验证分别记录：

| 维度 | 标记 | 含义 |
| --- | --- | --- |
| 实现 | 未实现 | 活跃 Linux 构建没有对应能力；占位页面、历史文档、归档代码不算实现 |
| 实现 | 部分实现 | 已交付该类功能的部分子能力，必须列出缺项 |
| 实现 | 接口已实现 | 已有 Linux 接线与控制逻辑，但仍受设备、驱动、权限及实测范围限制 |
| 软件 | 未验证 | 没有对应功能的通过记录；通用构建成功不能代替功能测试 |
| 软件 | 软件通过 | 存在明确的单元、故障注入或界面夹具通过记录，仅覆盖记录中的场景 |
| 真实验证 | R0 | 未有对应操作的实机通过记录；接口被发现也不算实际调节成功 |
| 真实验证 | R1 | 已观察真实状态、设备或原生窗口；不代表写入成功或测量精度已校准 |
| 真实验证 | R2 | 指定真实操作的写入、状态读回或可观察效果通过；不代表带载效果 |
| 真实验证 | R3 | 指定负载、供电、时长及停止阈值下的效果已验证；必须附报告 |
| 生命周期 | L0 | 未验证实际生命周期恢复 |
| 生命周期 | L1 | 仅已列出的部分恢复路径通过，例如显式释放、手动切回原模式 |
| 生命周期 | L2 | 该功能定义的生命周期清单全部通过；需逐项记录异常退出、租约、断电、休眠/唤醒、重启等适用场景 |

R 与 L 是独立维度。五秒强冷后显式释放可以记为 R2/L1，不能记为带载验证或完整生命周期验证。软件中的休眠、回滚、超时故障注入也不提高真实 L 等级。硬件无关的纯 UI 能力使用 R1 描述原生窗口验证，硬件生命周期标为“不适用”。

本台账尚无 R3 或 L2 的硬件控制条目。标准接口代码可在其他机器上发现能力，但未形成其他机型的实测支持承诺。

## 能力边界与逐项证据

### ORL-F001：系统与散热监测

- 实现/权限：E-C01 使用 procfs、sysfs、hwmon、power_supply；E-C03 补充 OEM 双风扇读数。读取以普通用户实际可见接口为准，未知/故障值不回退模拟数据。GPU 专项边界见 ORL-F007。
- 软件：E-S01 覆盖单位换算、坏值、缺失数据、CPU 差分、电池健康度等；E-S02 验证真实快照可到达原生窗口。真实 R1 来源为 E-H01/E-H02 的状态及风扇记录，不声称所有显示值均经外部仪器验证。
- 后续实现（E-S05）：标准 hwmon 和 CPU/内存/供电/静态身份增加来源、有效采样时间及 ok/unavailable/fault/warming_up；静态身份成功缓存，缺失每 30 秒重试。界面按单调时钟判断十秒未更新为过期，暂停新调节并停止续租，恢复操作保留。
- 下一步：补齐电池、背光、OEM 子字段元数据与历史缓存，实测进程开销；历史缓存不能隐式增加独显轮询。

### ORL-F002：系统档位与 OEM 模式

- 实现/权限：E-C02 经 power-profiles-daemon / tuned-ppd 协调系统策略；内核平台档位只接受公开值，服务管理同一策略时不争抢直接写入。OEM 模式由 E-C03/E-C04 执行事务，受 OEM-W 限制。切换成功后的模式驻留，退出不自动撤销。
- 软件与实机：E-S01/E-S02 覆盖非法档位、界面门禁与夹具；E-S03 覆盖 OEM 事务故障。E-H01 记录办公连续五次、接电均衡/狂暴及恢复的 R2/L1。E-H03 的系统 `power-saver → balanced → power-saver` 为 `0.9.3-linux.1` 历史 GUI 证据；E-H02 中 `0.9.3-linux.2` 的系统/平台两项真实写回均跳过，不算新版重验。
- 下一步：按系统层/OEM 层分别验证负载效果、会话变化与生命周期；用户配置不能混淆两类档位。

### ORL-F003：CPU 功耗、风扇曲线与强冷

- 实现/权限：E-C03/E-C04/E-C05 提供 OEM 三元功耗事务、八点风扇曲线、强冷及恢复。CPU 自定义值受出厂上限和组合约束；曲线要求供电、有效节点和保护条件。模式/功耗驻留，曲线/强冷有控制租约和释放语义。E-C02 另有已发现 hwmon/powercap 通道的通用控制，要求合法范围、SYS-W，不能作为主机型已有此通道的证据。
- 软件：E-S01 覆盖帧编码、协议版本拒绝、曲线校验、通用风扇恢复与功耗边界；E-S02 覆盖草稿、应用/恢复、供电门禁和 UI 故障态；E-S03 覆盖 333 个风扇、416 个模式/功耗/强冷故障注入点和对应生命周期模型。
- 实机：E-H01 只有 35/35/70 W 三元功耗读回、切回原模式以及五秒强冷后显式释放；E-H02 重验完整包的五秒强冷，读数 5085/5210 RPM 并恢复。均为 R2/L1，不证明 CPU 实际耗电、持续散热或完整生命周期。自定义风扇曲线没有真实应用通过记录，仍为 R0/L0。
- 下一步：另行安排授权的保守带载、真实曲线、异常退出、租约过期、断开原装电源、休眠/唤醒和重启清单；记录每个子能力，不能整行统一升级。草稿已迁入 XDG 配置，旧 localStorage 副本保留，导入/保存均不自动应用；新实现的实机恢复行为仍待独立复验。

### ORL-F004：电池养护与限充

- 实现/权限：E-C01 仅在电池已发现、公开 `charge_control_end_threshold` 且可写时设置；验证取值与起始阈值关系并读回。HW-01 当前未公开该接口（E-H01），因此是“接口已实现但本机不可用”，不能标为主机型已支持限充。
- 软件：E-S01 覆盖边界、未知电池、起始阈值和不凭空创建接口；无真实限充写入证据。电池状态/健康度展示归 ORL-F001。
- 下一步：核实主机型 OEM 协议、真实充电行为及恢复条件；需要新协议时通过硬件字典与语义操作实现，不开放裸寄存器入口。

### ORL-F005：屏幕与单色键盘亮度

- 实现/权限：E-C01 仅发现 backlight 与键盘背光 LED，E-C02 使用 logind `Session.SetBrightness`；需要活动会话授权。目标发现、范围及路径边界有 E-S01 覆盖；这不验证每种桌面授权行为。
- 既有实机边界：E-H03 中 `0.9.3-linux.1` 的屏幕亮度直接 logind API 调用读回及恢复成功（API 层 R2/L1），同次 GUI 键盘操作的 `changed_through_gui` 为 `false`。不能将其写成 GUI 端到端成功，也不能直接继承为当前版本通过。单色键盘亮度无专项通过记录。
- 下一步：保留该历史未闭环项，验证当前版真实 GUI 提交、权限被撤销、设备切换与恢复；多色 RGB 单独按 ORL-F006 交付。

### ORL-F006：RGB 键盘、灯带与灯区

- 证据/边界：E-C06 显示尚待 Linux HID 传输适配；活跃命令清单 E-C07 无 RGB 动作。旧效果引擎、历史协议及样例不构成 Linux 功能或验证证据。
- 下一步：先确定设备标识、接口及协议；设备确为 HID 时再选择传输实现。先交付基础颜色/亮度与固件效果，再验证分区、灯带、软件帧效果及退出恢复。设备范围当前为“待确认”，不直接继承 HW-01 的 EC 支持。

### ORL-F007：GPU 状态与能耗

- 实现/权限：E-C01 读取已发现 hwmon；E-C06 按设备名挑选温度/功率用于展示。E-S01 的 `suspended_gpu_is_not_polled` 验证跳过休眠设备，但它是模拟系统接口测试。没有完整适配器清单、GPU 利用率/显存、驱动状态或能耗评估闭环。
- 验证：通用 hwmon 软件通过不能证明真实 NVIDIA/AMD 独显不会被唤醒；现有硬件报告未建立逐 GPU 测量与休眠专项结论，保持 R0。
- 下一步：识别适配器、集显/独显与运行时电源状态，按需采样并测量闲置/最小化功耗与唤醒；不要以固定轮询换取更多默认字段。

### ORL-F008：GPU Dynamic Boost、TGP 与超频

- 证据/边界：E-C06/E-C07 没有专用 GPU 调节命令。E-C02 的通用已发现功耗上限是独立能力，不能等同于 Dynamic Boost、TGP 偏移或频率超频，也没有这些功能的实测范围。
- 下一步：分别记录 GPU、驱动版本、OEM 协议、供电条件、合法限值及恢复方式；每个控制独立验收，不以 Windows API 的存在推定 Linux 等价能力。

### ORL-F009：GPU MUX 与显卡拓扑

- 证据/边界：E-C06 显卡模式页明确占位，E-C07 无切换命令；应用渲染选择、物理 MUX、外屏拓扑均未形成 Linux 工作流，无可写设备范围。
- 下一步：先识别拓扑，再区分进程 offload 和物理切换；物理 MUX 的授权测试需覆盖重启、外屏、恢复与失败提示。

### ORL-F010：BLE 水冷

- 证据/边界：E-C06 为 BlueZ 后端待实现提示，E-C07 无连接或调节命令；没有已验证蓝牙设备、配对/会话权限或断线行为。
- 下一步：获得设备后实现发现、连接与遥测，再增加保守调节；确认脱离主机后的自主保护及最后设置行为，分别记录权限、断连和恢复测试。

### ORL-F011：全局快捷键、OSD、机身按键

- 证据/边界：E-C07 仅有窗口、托盘、自启和硬件 IPC；尚无 Linux 快捷键注册、OSD、机身事件订阅。现有模式轮询只显示状态，不能证明消费了按键事件。
- 下一步：先按桌面实际能力提供快捷键及通知；按 GNOME/KDE、Wayland/X11 分开记录注册授权、冲突、注销与快捷操作结果。机身按键单独关联硬件事件和模式读回。

### ORL-F012：托盘快捷控制与刷新率

- 实现/权限：E-C07 的托盘仅提供“打开 OpenRevo”和“退出”，托盘不可用时不阻止 GUI；没有快捷硬件菜单、迷你抽屉或刷新率接口。
- 验证：E-S02/E-H02 证明原生窗口与桌面启动，未覆盖托盘点击专项或 GNOME/KDE 托盘扩展组合；因此不将整个功能记为 R2。刷新率功能未实现，无权限或显示设备支持承诺。
- 下一步：复用同一语义 API 添加常用控制，明确窗口关闭与后台策略行为；刷新率按桌面显示接口另行调查和验证。

### ORL-F013：摄像头、触控板、Win 键等开关

- 证据/边界：E-C07 无这些独立动作；OEM 模式事务保存/恢复某些相关固件状态，不等于已经提供用户开关。没有独立的 Linux 权限、设备发现或实测记录。
- 下一步：逐项区分桌面设置、输入事件过滤、固件开关与硬件断电，选择能读回并解释真实效果的接口；不得将软件禁用标成硬件关闭。

### ORL-F014：MiniLED、通电开机等固件功能

- 证据/边界：E-C07 无这些独立命令，未建立受支持屏幕、BIOS 或固件功能清单；历史 Windows 资料只作为调查线索。
- 下一步：按子功能追加稳定子 ID、设备匹配和协议证据；明确立即生效/重启生效、恢复方法以及用户可观察的结果后再开放写入。

### ORL-F015：自动化规则与场景切换

- 证据/边界：E-C05 只有手动曲线草稿，E-C07 只有登录自启和单客户端控制；无命名场景、规则执行器、控制 CLI 或独立后台 agent。现有内核保护与看门狗不是通用自动化规则。
- 后续基础（E-C09、E-S05）：已提供曲线草稿 v1 的 XDG 保存、迁移、导入导出和备份；状态查询不续租，显式主窗口续租独立执行。配置错误具有 code/message，硬件命令错误仍以字符串为主。
- 下一步：命名场景、结构化能力/硬件错误、事件和控制所有权；再做可暂停、可解释的规则。当前是单 GUI 所有者，进程内配置串行不等于跨进程事务，多客户端行为需单独验收。

### ORL-F016：用户插件与机型配置

- 证据/边界：E-C08 明确旧插件和 `models.json` 文档仅供 Windows 历史参考；E-C07 没有 Linux 插件安装/执行或用户机型配置接口。驱动的内部 DMI/BIOS 白名单是安全匹配，不是可由插件或用户配置扩大的模型库。
- 下一步：先提供受校验的数据配置、机型证据条目、版本化 Linux SDK 和样例；隔离代码扩展随后实施。引入第三方内容前审查 CSP、逐窗口能力与自定义 IPC 授权；插件不得直接取得设备、EC 地址或完整宿主权限。历史 manifest 不承诺直接兼容。

## 后续更新的验收要求

1. 新功能或改变行为时更新对应稳定 ID，列出实现范围、当前设备可用性、权限、软件用例、真实等级和下一步；缺证据保持未验证。
2. 每次真实验证记录应用/模块版本、DMI/BIOS、内核、设备/驱动版本、供电、初始状态、操作、观察结果、恢复结果与原始报告位置。时间统一注明时区。
3. 编译、模拟故障、原生 UI 夹具、接口读回、负载效果与真实生命周期分别记账。失败、跳过、仅 API 成功而 GUI 未成功的记录不得省略。
4. 机型/BIOS、驱动或行为变化后保留旧结果所属基线，新增复验结果；不把旧版成功默认升级到当前版本，也不静默删除曾失败的证据。
5. 本台账与离线验证不授权安装/替换模块或真实硬件调节。带载、曲线、断电、休眠和重启等测试另行明确范围后执行。
